# 故障对照表

> 何时读：任一环节报错、结果不符合预期、用户反馈「下不动/搜不到/字幕不对」时先查本表，
> 再决定是重试、换策略还是如实上报。日常顺利的流程不需要读。

## 一、排查顺序

按成本从低到高，不要跳步：

1. **看 JSON 输出的 `status` 与 `message`**——大多数问题的原因字段里已经写了，
   不要从自然语言日志里猜。
2. **跑只读巡检**：`doctor sources`（源可达性）、`doctor library`（库一致性）、
   `doctor fs`（文件系统能力）。`doctor` 不改动任何东西，先体检再动手。
3. **再看网络与代理**：确认代理配置与实际网络情况。
4. **最后才换策略**（换源、换片源版本、改下载方式），并把换了什么、为什么换讲清楚。

## 二、搜不到 / 结果不相关

| 症状 | 原因 | 处理 |
|---|---|---|
| `count: 0`，源明确返回空 | 该源确实没有这个条目 | 换检索名（用元数据里的另一种语言名）重试；仍为空则换源/改用合集名检索 |
| 返回几十上百条但条条不相关 | 源侧对无法分词的查询退化成「最新上传流」 | 词元闸门应已丢弃这些结果；丢弃后为空就如实报告「该源不支持此查询」，换源或换拉丁检索名 |
| 中文查询在某个源上恒为空 | 该源 `query_script` 为 `latin`，不处理中文 | 改用元数据给出的拉丁名检索；或只把中文交给 `both` 类型的源 |
| 拉丁查询大小写不同结果差异巨大 | 部分源区分大小写 | 用小写与首字母大写两种变体各试一次，合并结果再排序 |
| 片名对但年份/续集错位 | 同名作品多，或结果是续集 | 用元数据里的年份核对；确认目标片名不含序号时，续集候选要单独说明 |
| 单集恒无结果 | 冷门/老番单集源普遍无种 | 改走合集路线（见下文「选中了文件却没数据」） |

**不要**为了凑出结果而关掉词元闸门。空结果是有用信息，误导性结果是净损失。

## 三、下载没速度 / 卡住

| 症状 | 原因 | 处理 |
|---|---|---|
| 进程起了但长时间 0 速度 | 该磁力已无做种者，或 tracker 全不可达 | 换下一个候选（优先种子数高的）；把候选差异讲给用户 |
| 有 peers 但速度极低 | peers 不可连通，或带宽受限 | 继续观察，但提前告知用户预计耗时；超过合理时限就换候选 |
| 连接立刻失败、退出 | 代理不可用，或代理类型不被支持 | 见下方代理条目 |
| 磁盘空间不足 | 目标盘写满 | 先 `index stats` 给出库里占用情况，让用户决定清理还是换盘 |
| 下载目录被预分配占满 | 未关闭预分配 | 预分配必须关闭，否则测试性下载也会吃满磁盘 |
| 进度反复回退或文件重新拉 | 目标目录里有同名残留文件 | 检查目标目录，让用户决定删除残留还是换目录；**不要自动删** |

**代理相关（重点）：**

- 下载引擎**不支持 SOCKS 代理**。把 `socks5://…` 填进代理配置会导致进程直接报
  「unrecognized proxy format」并退出。需要走 SOCKS 时用系统级 TUN/透明代理，
  或改用 HTTP 型代理地址。
- 代理配置为空串表示**用户要求直连**，不要自作主张回退去读环境变量。
- 代理地址写错（缺 scheme、缺端口）的表现与「源挂了」极像。先确认代理格式，
  再怀疑源。

**DHT 与 tracker：**下载引擎内置的可用集合是筛选过的结果；公共 DHT 入口和 tracker
里失效者居多。遇到「有 metadata 但始终连不上 peer」，先确认内置集合未被配置覆盖。

## 四、选中了文件却没数据

| 症状 | 原因 | 处理 |
|---|---|---|
| 目标集文件是 0 字节 | 选集下载会为未选中的文件留 0 字节占位；或索引选错 | 核对索引是否指向目标集；0 字节文件在归档时会被跳过，不需要手工清理 |
| 下了一整季而不是一集 | 未传 `--select`，或索引定位失败回退整季 | 定位失败时应先问用户，不要默认整季下载 |
| 索引对不上目标集 | 文件列表编号是 1 基，与集号不是同一个东西 | 先取 metadata 得到文件列表，按集号匹配出索引再下载；集号与索引混用是常见错因 |
| 集号匹配不上 | 合集里命名不规范（无季集号、中文集号、裸数字） | 依次尝试多种集号模板；都不行就报告「无法在合集里定位第 N 集」，不猜 |

**老番单集破局的正解**是合集选集，不是反复换单集磁力：单集源普遍无种，
转换策略比重复重试更快。

## 五、字幕问题

| 症状 | 原因 | 处理 |
|---|---|---|
| 检索返回空 | 该片源版本没有对应字幕，或查询词不合适 | 换片源版本、或换合集版本；仍无则如实报告并给手动补齐建议 |
| 请求被拒 / 空响应 | 未使用播放器风格 User-Agent | 按字幕站要求设置请求头后重试 |
| 请求 302 到异常地址 | 查询词含大写 ASCII 字符 | 查询词统一转小写后重试 |
| 下载到的不是字幕文本 | 下载链接指向 gz 压缩包 | 按 gz magic 判断并解压，不要按 URL 后缀判断 |
| 字幕里出现推广行 | 字幕站返回正文夹带署名/推广 | 走清洗流程；推广行与正文挤在同一块时逐行剔除，绝不整块丢弃 |
| 清洗后几乎没有汉字 | 拿到的不是中文字幕 | 判为失败，如实上报，不要当作成功落地 |
| 时间轴对不上画面 | 字幕与片源版本不一致 | 见下方「字幕错位」 |
| 已有中字却被判为无 | 外挂字幕带语言后缀（`Movie.cht.srt`），同名比对漏判 | 剥掉语言后缀后再比对主名 |

**字幕错位（时间轴不匹配）处理顺序：**

1. 确认字幕名里是否带 release 组名，与视频版本是否一致。
2. 不一致 → 回字幕站换一个与该版本对齐的候选（优先下载次数高的）。
3. 没有对齐的候选 → 如实告知用户「找到的是通用版本，可能与你的片源时间轴有偏移」，
   并说明播放器侧可手动微调字幕延迟，skill 侧不代做帧级修正。
4. **不要**用「换一个差不多的字幕」来掩盖：错轴字幕对用户是纯负担。

## 六、归档与硬链接失败

| 状态码 / 症状 | 原因 | 处理 |
|---|---|---|
| `skipped-exists` | 目标路径已有同名文件 | 默认不覆盖。报告给用户，让用户决定替换、跳过还是改名 |
| `refused-large-copy-…` | 源与目标不同文件系统，回退复制被体积闸门拦下 | 说明「复制会额外占用 N GB」，等用户显式放行后再执行 |
| `hardlink-unavailable-EXDEV+copied` | 硬链接要求同文件系统同挂载点，跨挂载点不可用 | 已回退复制并保留源文件；把实际多占的空间告诉用户 |
| `hardlink-failed-<errno>+copied` | 同盘但 `link()` 仍失败（权限、配额、文件系统不支持） | 已回退复制；若频繁出现，建议改用 `move` 动作或把下载目录挪到库同盘 |
| `moved-cross-device-copied` | 移动跨设备，走了复制路径 | 正常结果，但要让用户知道多占了一份空间 |
| `error:source-missing` | 计划生成后源文件被移动/删除 | 重新扫描下载目录；不要靠缓存清单重复执行 |
| `error:path escapes library root` | 资源名含越界路径（`../`、绝对路径、指向库外的符号链接） | 拒绝归档并如实告知；这属于异常资源名，不做就近修正 |
| 归档后库里出现 0 字节文件 | 占位文件被当成内容 | 检查过滤规则；0 字节与 `.aria2` 必须跳过 |

**硬链接失败的常见误解**：硬链接不是「复制一个链接」，它要求源与目标在同一文件
系统。用户说「链接一下省空间」但下载盘与库盘是两块盘时，物理上做不到——
要么移动文件，要么接受多占一份空间。先做 `doctor fs` 探针确认能力，再给方案。

## 七、路径与权限

| 症状 | 原因 | 处理 |
|---|---|---|
| 目标目录不存在 | 库根未创建或路径写错 | `ingest` 会按规范创建子目录；库根本身不存在时如实报错，**不替用户创建**不确定的路径 |
| 权限拒绝 | 目标目录不可写，或运行用户与库属主不同 | 给出具体路径与建议（改权限/换目录），不要静默改权限 |
| Windows 上文件名非法 | 资源名含 `< > : " | ? *` 等字符 | 已统一替换为 `_`；若用户看到未替换的名字，说明该文件不是本工具写入的 |
| 库根是符号链接，落盘路径与预期不同 | 路径校验返回规范化绝对路径而非解析后的真实路径 | 这是刻意设计（避免把用户给的库根改名）；向用户解释时按实际配置路径说明 |

## 八、配置与状态目录

| 症状 | 原因 | 处理 |
|---|---|---|
| 改了配置没生效 | 改在了另一个状态目录（环境变量覆盖） | 用 `config` 输出里的 `state_dir` 确认实际生效的目录 |
| 配置损坏后行为异常 | 配置文件无法解析 | 读取配置失败时会回落默认值；报告里说明「已回落默认值」，并建议用户核对配置 |
| 索引与磁盘不一致 | 手工移动过文件，或换了机器 | `index rebuild --library <库根>` 从磁盘结构与文件名重建，不要手工改数据库 |
| 索引里出现数据库文件自身 | 索引库落在媒体库目录内 | 重建时已排除数据库与 WAL 影子文件；若看到条目异常，先确认条目路径扩展名 |
| 换个机器后 `doctor fs` 报硬链接不可用 | 库与下载目录不在同一文件系统 | 正常结果，按第六节处理；也可以在配置里把归档动作改成 `move` |

## 九、通用上报口径

故障报告固定包含四段，缺一段用户就没法决策：

1. **事实**：哪一步、什么命令、实际得到的状态码或错误原文。
2. **原因判断**：一句话说清是源侧、网络侧、磁盘侧还是用户输入侧的问题；
   无法判断时明说「原因未确定」。
3. **已尝试的动作**：换过哪些检索名/候选/源，结果如何——避免用户重复问一遍。
4. **建议的下一步**：给 2-3 条按成本排序的选项，并说明各自代价（耗时、额外空间、成功率）。

**禁止事项：**

- 不把「未找到」包装成「已为你处理好」。
- 不静默重试到用户察觉不到失败。
- 不为了让报告好看而省略体积、耗时等定量信息。
- 不在失败后自动执行写操作（重下、移动、删除）——所有落地动作都要用户确认。
