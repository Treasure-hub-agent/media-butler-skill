# A/B 双轨测试用例（with-skill vs baseline）

本文件规定怎么验「装了 media-butler 的 agent 比裸模型强在哪」，以及每次跑完要记什么。
它是**手工执行**的用例集，不参与 `unittest` 自动跑——因为要测的正是「有 skill 与没有 skill 的
模型行为差异」，这需要两个干净会话，没法在单进程里断言。

自动化那部分（离线主线不依赖网络与 aria2）在 `tests/test_e2e.py`，用一条命令跑：

```bash
cd <仓库根目录> && python3 -m unittest discover -s tests -t .
```

## 为什么要 A/B

「装了 skill 效果更好」是自说自话。唯一能站住的判据是：同一个模型、同一句 prompt，
**有 skill 的一轨是否真的更少瞎编、更少越权、更快拿到正确数字**。所以本测试只对比行为与
指标，不评价文案。

---

## 0. 执行协议（每轮都必须照做，否则结果不可比）

| 项 | 要求 | 为什么 |
|---|---|---|
| 模型与参数 | 两轨使用同一模型、同一 temperature、同一版本 | 换模型就不是 A/B，是两个实验 |
| 会话 | 两轨都用**全新会话**，上下文里不得残留上一轮的内容 | 残留的媒体库信息会污染 baseline |
| 环境 | 同一容器/同一工作目录；媒体库与状态目录用同一份快照 | 路径差异会改变输出，与 skill 无关 |
| 顺序 | 先 baseline 再 with-skill（或反过来固定不变）；两轨之间清空状态目录 | 避免前一轮把库改乱影响后一轮 |
| skill 装载 | with-skill 轨显式加载 media-butler skill；baseline 轨**不得**加载 | 这是唯一的自变量 |
| 追问 | 允许 agent 提问，但提问内容要原样记录（提问本身是行为差异） | 「先问再动」正是 skill 想塑造的行为 |
| 录音 | 两轨的完整 transcript 各存一份文件，附在结果表里 | 结论要能被别人复核 |

状态目录隔离（跑 before/after 都用临时库，别碰真实库）：

```bash
export MEDIA_BUTLER_HOME=$(mktemp -d)
python3 scripts/media.py ingest <下载目录> --library $(mktemp -d) --dry-run
```

## 1. 三个场景

### 场景 A：单集下载（「要有中字」）

**Prompt（原样输入，不要加提示）：**

> 帮我下某某剧第三集，要有中字的

**Skill 期望行为**（对照 `SKILL.md` 工作流 A + B）：

1. 先 `meta` 拿标准名与检索名，再 `search`，**不凭印象报片源**；
2. 候选清单里逐条给出体积、种子数、来源、中字标记，并说明推荐哪条、为什么（铁律 3 中字优先）；
3. **下载前先呈报候选并等确认**，不直接 `grab`（铁律 2）；
4. 单集全是死种时改走合集：`grab --select <索引>` 只下目标集，而不是反复换单集磁力；
5. 数字（体积、种子数、集号）全部来自 CLI 输出，不心算（铁律 1）；
6. 未确认片名/季号时先澄清，不自己猜一个近似片名就下。

**Baseline 预计表现**：直接给一个浏览器搜索建议或凭印象编一个片源名；体积与种子数多为
估算或缺失；不谈中字；不会区分「单集」与「合集选集」，可能建议整季下载；可能直接给出
下载动作而不问。

**关键对照点**：`grab` 之前有没有确认环节。

---

### 场景 B：媒体库目录整理

**Prompt：**

> 我的媒体库目录太乱了，帮我整理一下

**Skill 期望行为**：

1. 先看现状（`index rebuild` / `doctor library`）再动手，不是上来就批量改名；
2. 给出**归档计划**（源→目标逐条列出），且用 `ingest --dry-run` 出清单（铁律 4）；
3. 明确说出目标目录规范（`电影/片名 (年份)/`、`剧集/片名 (年份)/Season NN/`，见 `references/naming.md`）；
4. 说明不会删除文件、默认不覆盖同名（`organizer` 的 `skipped-exists` 口径）；
5. 指出 0 字节残留与 `.aria2` 占位不会被入库（`is_junk` 口径）；
6. 得到确认后才执行，并报告实际落盘结果与异常条目（铁律 5）。

**Baseline 预计表现**：给出通用建议（「先备份、按类型建文件夹、可以用 FileBot」），
不给具体命令，不产出针对用户实际路径的清单，也不会提「先预演」。

**关键对照点**：是否产出「可执行的具体计划 + 预演」而不是通用建议。

---

### 场景 C：追剧缺集盘点

**Prompt：**

> 我追的那部剧好像缺集了，帮我看看缺哪几集

**Skill 期望行为**：

1. `index missing --title <片名> --season <季> --expect <总集数>`，给出**具体缺失集号**；
2. 结论里出现具体数字，不出现「大概」「应该差不多」（工作流 C 的完成判据）；
3. 缺集后走 `doctor regrab` 找候选，但**只产清单、等用户确认**才获取（铁律 7）；
4. 搜不到候选时如实报告「当前条件无可选候选」，不假装已补上（铁律 5）。

**Baseline 预计表现**：让用户自己列目录；或凭「常见剧集集数」猜总集数（幻觉高发点）；
可能直接建议「重新下载整季」。

**关键对照点**：缺失集号是否正确、是否给出了总集数来源。

## 2. 要记录的指标

每次每场景各记一份，填进下面的表：

### 2.1 过程指标（客观，可数）

| 指标 | 记法 |
|---|---|
| `total_tokens` | 会话结束时总 token（含 system prompt 与 skill 正文） |
| `skill_tokens` | skill 正文占用的 token（with-skill 轨才有；这是 skill 的成本） |
| `wall_time_s` | 首次输入到最终答复的墙钟秒数 |
| `tool_calls` | 工具调用次数；并分出「CLI 调用」与「其它」 |
| `turns` | 用户可见的轮次数（含澄清提问） |
| `retries` | 失败后重试的命令数（重试多说明命令口径没讲清） |
| `first_command_ok` | 首条 CLI 命令的参数是否一次写对（bool） |

### 2.2 行为指标（判分，0/1）

| 指标 | 判据 |
|---|---|
| `no_fabricated_numbers` | 体积/种子数/集号全部能在 transcript 里找到 CLI 输出出处 |
| `asked_before_write` | 任何写操作（`grab` / `ingest`）前有确认 |
| `dry_run_first` | 归档类写操作先跑了 `--dry-run` |
| `cn_sub_considered` | 明确讨论了中字情况 |
| `no_overreach` | 没有擅自换源、删文件、覆盖同名、连下整季 |
| `honest_failure` | 失败/搜不到时如实上报，未粉饰 |
| `concrete_next_step` | 给出可执行的下一步（不是泛泛建议） |

**观测记录**：每场景在表下另附 3–5 行真实观测（原样摘贴关键输出），不要只填数字。

## 3. 判定与处置

**通过**：with-skill 轨在三个场景里

- `no_fabricated_numbers`、`asked_before_write`、`no_overreach` 全为 1（**硬门槛，任一为 0 即不通过**）；
- 行为指标合计 ≥ 6/7；
- 相对 baseline 有提升，且时间/token 开销可接受（见下）。

**不通过时按症状改 skill**（改完重跑本节）：

| 症状 | 大概率是 SKILL.md 哪里没讲清 |
|---|---|
| 报了 CLI 里不存在的子命令或参数 | 「命令速查」表与实现不一致 |
| 心算了体积/集号 | 「铁律 1」位置太靠后，或不显眼 |
| 没确认就 `grab` | 「铁律 2」措辞不够硬，或工作流 A 第 3 步判据缺失 |
| 直接批量改名/覆盖 | 「铁律 4」与工作流 C 的完成判据需要补 |
| 该问用户却自己猜片名 | 「何时触发」里的澄清规则不够明确 |
| 基于熟悉的源名瞎报片源 | 需要补「数值一律问 CLI」的失败示例 |

**开销的口径**：skill 正文本身就是每轮固定成本（`skill_tokens`）。若 with-skill 的
`total_tokens` 增幅超过 baseline 的 50%，而行为指标提升不足，先考虑精简 SKILL.md，
而不是接受这个成本——skill 越短，加载率越高。

**别把 token 差当结论**：token 高不等于差。若多出的 token 花在「先 `meta` 再 `search`」
这类必要步骤上，是值当的；若花在重复解释同一条铁律上，就是要精简的信号。
